C1Google Project Zero Accelerates to Full 30-Day Disclosure by 2028 — AI-Assisted Exploitation Makes Old Timelines Obsolete

📰 Article (English)

Google Project Zero has announced a major overhaul of its vulnerability disclosure policy, citing AI-assisted discovery and exploitation as the key driver. The team argues that the previous "90 + 30" days framework — 90 days to fix plus 30 days for patch rollout — is "clearly insufficient" in an era where AI tools dramatically shorten the time between vulnerability discovery and working exploit development. The new policy transitions in three phases: starting now at a full 90-day deadline, moving to 60 days on February 2, 2027, and reaching 30 days on January 3, 2028. Crucially, the grace period and special variant-bug policy have been entirely removed to simplify the framework and allow both sides to automate compliance tracking. Remaining exceptions are narrow: vulnerabilities being actively exploited in the wild follow Google's separate application security policy, and Project Zero may publish earlier if another party has already disclosed the details. Vendors can also request early publication. The stated goal is to close the "patch gap" — the lag between a vendor shipping a fix and users actually installing it. By compressing disclosure timelines, Project Zero aims to increase pressure on both vendors to fix faster and users to update promptly. Hardware vulnerabilities (like Spectre and Meltdown) remain eligible for case-by-case exceptions.

C3PyPI Redesigns Project Pages with Security Signals — Provenance, Attestations, and Supply Chain Warnings Now Live

📰 Article (English)

PyPI has completed a major redesign of its project pages, adding a dedicated Security tab with clearer supply chain signals. Built in partnership with Kabu Creative and funded by OpenSSF, the update brings cryptographic provenance verification to every package page on the Python Package Index. The new Security tab shows each release's provenance state: "Full provenance" means every file in the release has an attestation — either a PyPI Publish attestation (confirming a Trusted Publisher uploaded it) or a SLSA Build Provenance attestation (linking the file to its exact source commit, build platform, and build instructions). "No provenance" means no cryptographic verification is available, though this doesn't imply maliciousness. Warning states added include: Incomplete (some files attested, others not), Inconsistent (files in one release from different repos or build systems), Change of provenance (repo or workflow changed from previous release), and Loss of provenance (a project that previously published attestations now uploads without them). The release files tab now shows per-file provenance and flags late files — those uploaded more than 14 days after the release timestamp — which is a known supply chain attack vector. Release history shows file count, provenance state, and quarantine/yanked status at a glance. PyPI also published an expanded package security guide covering source code security, provenance, package integrity, common attacks, and reporting.
