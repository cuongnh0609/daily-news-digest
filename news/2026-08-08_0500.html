B1LLM WikiパターンをOKFで標準化——エージェントが業務知識を体系的に管理・参照する新仕様

📰 本文 + 和越対訳

Google Cloudが2026年6月に発表したOKF（Open Knowledge Format）は、AIエージェントが過去のやりとりや業務知識を構造化・再利用可能な形式で管理するための仕様である。Markdownファイルとメタデータを組み合わせた設計で、複数のエージェントやツール間でナレッジのポータビリティを実現する。従来のRAG（Retrieval-Augmented Generation）アプローチはチャンク間の関係性が失われがちで、毎回ゼロからの知識再構築を余儀なくされていた。OKFはこの問題に対応し、「LLM Wiki」という概念——つまり過去の会話から構造的な知識を積み上げる手法——を標準フォーマットとして定義する。パーサーを一度実装するだけで複数のバンドルに適用できる点が実用上の大きな利点とされている。一方で、「意味の統一」まではカバーしておらず、LLMが一貫した品質でMarkdownを生成する難しさや更新メカニズムの運用負荷は引き続き課題として残る。

OKF (Open Knowledge Format) do Google Cloud công bố tháng 6/2026 là một đặc tả cho phép AI agent quản lý và tái sử dụng kiến thức nghiệp vụ dưới dạng có cấu trúc. Thiết kế kết hợp file Markdown với metadata giúp chia sẻ knowledge giữa nhiều agent và công cụ khác nhau. Phương pháp RAG truyền thống thường mất đi mối liên hệ giữa các chunk và phải xây dựng lại kiến thức từ đầu mỗi lần. OKF giải quyết vấn đề này bằng cách chuẩn hóa khái niệm "LLM Wiki" — tức là tích lũy kiến thức có cấu trúc từ các cuộc hội thoại trước đó. Ưu điểm thực tế lớn nhất là chỉ cần viết parser một lần là có thể áp dụng cho nhiều bundle khác nhau. Tuy nhiên, OKF chưa giải quyết được vấn đề thống nhất "ngữ nghĩa" và việc LLM tạo ra Markdown chất lượng đồng đều vẫn còn là thách thức.

📰 Article (English)

The pgrust project has published a detailed engineering post explaining how version 0.2 of its Rust-based Postgres query engine achieves approximately 300x faster analytical query performance compared to standard Postgres. The core insight is that Postgres was designed in the 1980s when disk I/O was the primary bottleneck. Modern workloads where datasets fit entirely in RAM are CPU and memory bandwidth-constrained, making the original row-at-a-time Volcano execution model deeply inefficient. Three optimizations compound to close this gap: First, batching processes 1,024 rows at a time instead of one row per next() call, reducing function call overhead and enabling CPU pipelining — bringing execution from 1.3 seconds to 480ms. Second, operator fusion collapses sequential scan and aggregation into a single processing node, eliminating inter-stage data copying and reaching 358ms. Third, SIMD (Single Instruction, Multiple Data) vectorization uses CPU-level parallelism to process multiple values simultaneously, achieving 135ms total. Each optimization is additive and independently meaningful. The post provides concrete benchmarks and Rust implementation details, making it directly actionable for anyone building analytics layers on Postgres.
